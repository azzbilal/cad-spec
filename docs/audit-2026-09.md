# cad-spec: repository audit and upgrade roadmap

**Audit date:** 23 September 2026  
**Repository snapshot:** [`azzbilal/cad-spec` at `0a823ed`](https://github.com/azzbilal/cad-spec/tree/0a823ed6b864c57456a139389fc5b515acc21ca0)  
**Purpose assessed:** a reinforcement learning environment that turns written mechanical specifications into CadQuery programs and scores the resulting boundary representation against measurable requirements.

## Executive assessment

**Current assessment: 6.5/10 overall** — roughly **6/10 for research differentiation** and **7/10 for technical substance**. These are judgment scores, not benchmark measurements. The project has a credible core: executable CAD scoring, partial credit, anti-cheat gates, seeded parameter variation, adversarial cases, and a four-job Linux/Windows CI matrix. The [latest CI run for this commit succeeded](https://github.com/azzbilal/cad-spec/actions/runs/35865829883). Its claim to inspect *requirements* is valuable, but recent work already uses executable CAD tests, and the current task is a single, heavily scaffolded plate template. A documented full-credit geometry error, no current model baseline, and thin evidence of generalization keep it below an 8 today.

**Best positioning:** an **open, inspection-style RL reward environment for dimensioned parametric parts**, with a rigorously audited scorer and published learning curves. It should not present itself as a broad text-to-CAD benchmark or a manufacturing-validity certificate. The word “material” in the current rubric means **volume consistency**, not actual material properties, strength, fit, or fabrication feasibility.

**Shortest route to 8/10:** close the scoring gap below, validate the evaluator against adversarial and human-reviewed examples, publish reproducible pre/post-training results on held-out prompts, and make installation/docs accurate. **Route to 9/10:** show a distinctive, transferable method for checking requirement compliance across several part families, prompt styles, and controlled edits, with external comparisons and measured engineering validity.

| Dimension | Current | Evidence needed for 8/10 | Evidence needed for 9/10 |
|---|---:|---|---|
| Innovation and differentiation | 6/10 | Mutation-validated inspection reward and a clear comparison with CADTests and similarity-based metrics | Transferable requirement-to-feature method, measured on new families and edits |
| Engineering substance | 7/10 | Both scoring errors below fixed; tolerances, datums, ambiguous features, and execution limits specified | Expert-checked functional constraints and reliable performance across richer geometry |
| Empirical evidence | 4/10 | Frozen v0.2 baseline, ablations, repeated-seed pre/post-training results | External benchmark comparison and statistically supported transfer results |
| Repository readiness | 7/10 | Clean quick start, current docs, reproducible environment and results artifacts | Versioned release with data card, failure taxonomy, and outside reproduction |

The overall judgment weighs **correctness and demonstrated learning value** most heavily. A green CI run verifies existing assertions; it does not measure whether those assertions fully capture mechanical intent.

## What was inspected

I reviewed the code, test fixtures, README files, roadmap, package metadata, CI workflow, and repository history at the pinned commit. The generated split contains **200 train and 30 eval specs**, and a direct sampler check found **230 unique parameter tuples**; eval includes area extremes (eval area 1,548–32,100 mm²; train area 3,648–25,228 mm²). This demonstrates parameter separation, not transfer to new part types or new ways of stating a requirement. The repository's own model baseline is explicitly marked as predating v0.2.0. I also checked the public CI result. See the verification note at the end for local test status.

## Findings, ordered by impact

### P0 — A plate can violate its edge margins and still receive 1.0

The prompt says the plate is centered on the origin and requires a specified edge margin. The scorer checks the **size** of the bounding box and **absolute** hole centers, but it does not check the box center or the hole-to-edge distances. Its material check uses volume, which is unchanged by translation. For the 80 × 60 × 6 mm sample with four Ø6.5 mm holes and a 10 mm margin, translate only the plate **+2 mm in X** while cutting holes at the nominal global positions `(±30, ±20)`. The left and right margins become **8 and 12 mm**. **I ran this model through the scorer: all four gates and all seven requirements passed, producing reward 1.000.** The core of the reproduction is:

```python
result = (cq.Workplane("XY").box(80, 60, 6)
          .translate((2, 0, 0))
          .faces(">Z").workplane()
          .rect(60, 40, forConstruction=True).vertices().hole(6.5))
```

**Fix:** record envelope min/max coordinates (or a validated datum frame) and measure each hole center's distances to the relevant four edges. Add a named edge-margin requirement and a centered-origin check if origin placement is truly part of the contract. Run this case against the changed scorer and verify it loses the correct requirement without an unrelated hard gate. **Where:** [tasks.py][tasks], [measure.py][measure], [rubric.py][rubric].

### P0 — A valid through-hole construction can receive zero

The hole detector groups cylindrical faces but records depth as the **maximum individual face height**, not the union of their axial spans. A cutter extruded symmetrically through the 6 mm plate (`.extrude(10, both=True)`) leaves two 3 mm cylindrical faces per hole in this CadQuery/OCP build. The resulting part has the same volume, dimensions, diameters, and four through bores as the reference. **I ran it: the detector recorded each depth as 3.0 mm, `simple_through_holes` failed, and raw reward was 0.000.** This makes the score depend on a modeling operation that does not change the specified part. The core construction is:

```python
base = cq.Workplane("XY").box(80, 60, 6)
cutters = (cq.Workplane("XY")
           .pushPoints([(-30, -20), (-30, 20), (30, -20), (30, 20)])
           .circle(6.5 / 2).extrude(10, both=True))
result = base.cut(cutters)
```

**Fix:** keep Z intervals for every cylindrical face in each coaxial diameter group, merge contiguous intervals with kernel tolerance, and compare their union to the actual plate top and bottom. Compute cylinder completeness against the merged axial coverage rather than one face's height. Add this cutter case, a seam-split bore, and a truly blind bore as separate regression cases. **Where:** [measure.py][measure], [test_measure.py][testmeasure], [harness][harness].

### P0 — The isolated worker is persistent and is not a security boundary

`build()` executes generated Python with `exec`. The worker changes its current directory to a temporary folder once and then reuses the process for later rollouts. A timeout controls duration, but the submitted code still has the worker's file, environment, and network access; it can also mutate state that later requests inherit. The source itself calls this “containment, not a security boundary.” The README language that the worker cannot dirty the workspace is too broad for ordinary Python code with absolute paths. **Where:** [measure.py][measure], [root README][rootreadme].

**Fix:** run untrusted rollouts in a disposable OS-level sandbox with restricted filesystem mounts, no secrets, network policy, process and memory limits, and per-rollout cleanup. Keep the in-process switch only for trusted debugging. Add a two-rollout state-leak test and a side-effect test in a safe test directory. Document the threat model before inviting external users to run arbitrary model output.

### P1 — The published “CadQuery only” quick start is incomplete

The root README says `pip install cadquery` is sufficient before running `scripts/test_rubric.py`. The script imports `cad_spec.rubric`, but the package lives under `environments/cad_spec`, and `cad_spec/__init__.py` immediately imports `environment.py`, which imports `verifiers` and `datasets`. The advertised command therefore needs the package and those dependencies installed, even though the rubric itself does not use them. `scripts/eval_local.py` also assumes package installation. **Where:** [root README][rootreadme], [__init__.py][init], [harness][harness], [eval_local.py][evallocal].

**Fix:** remove eager `environment` import from the package initializer or make the environment entry point lazy, then publish and CI-test a clean-room install command. Give separate exact commands for the lightweight rubric harness and the full Verifiers environment. Avoid implying that a source checkout alone makes `cad_spec` importable from the repo root.

### P1 — The evaluation mostly tests filling in a template

Every generated prompt gives the exact CadQuery operation sequence and asks the model to replace `???` numbers “and change nothing else.” The split varies five numeric parameters in one plate family, with 30 area-stratified eval cases from the same sampler. This is a legitimate **numeric precision and template-completion task**; it does not demonstrate open-ended engineering specification interpretation, model planning, or transfer to unseen geometry. The README's “generalization, not memorization” wording needs that narrower definition. **Where:** [tasks.py][tasks], [root README][rootreadme].

**Fix:** retain the current template task as **Level 0**, then add distinct held-out tiers: unscaffolded equivalent prose, paraphrased callouts, controlled dimension edits to an existing part, and eventually new feature/part families. Freeze those tiers before training and report each separately. Do not mix new task difficulty into one mean reward.

### P1 — Reward validity has no independent benchmark evidence yet

The adversarial harness has **21 named cases** in this commit, largely built from one spec, and reference solutions are checked on three seeds. These tests show the scorer behaves as expected on selected examples; they do not estimate how often a wrong part scores full credit or a valid part is rejected. The current docs' quoted baseline comes from the older six-check, 10-spec setup, so it cannot support a v0.2.0 training claim. **Where:** [harness][harness], [test_environment.py][testenvironment], [environment README][envreadme].

**Fix:** create a reviewed mutation set: change exactly one geometric requirement at a time, plus benign edits, compensated volume changes, shifted stock, broken-out holes, and numerical boundary cases. Record expected check results, not just expected total scores. Report false-full-credit and false-rejection rates and review disputed cases with a mechanical designer. Run at least two model baselines and a pre/post-training comparison on frozen, unseen examples.

### P2 — The hole detector has a documented asymmetric failure mode

Its full-cylinder area test silently drops bores intersecting another feature, a pocket, or the side wall. An off-edge hole may then lose both count and pattern credit, while other position errors lose only pattern credit. This may be acceptable for a simple plate curriculum, but it distorts reward smoothness and makes a broad “inspection report” claim too strong. **Where:** [measure.py][measure].

**Fix:** distinguish `closed_bore`, `partial_bore`, and `unclassified_cylindrical_feature` in the measurement report; test whether a conservative partial-bore position check improves reward alignment without admitting fillets. Keep the old reward as an ablation comparator.

### P2 — Repository presentation is ahead of its evidence

The source README says **20** harness cases, the harness contains **21**, and the pytest wrapper docstring says **19**. The roadmap's Phase 4 still calls for a commit/push although the code is on GitHub with successful CI. Its link to `.opencode/plans/cad-spec-elite-v0.2.0.md` points to a file absent from the tracked repository. The CI badge remains a placeholder; there is no tracked license, release, or current results artifact. **Where:** [root README][rootreadme], [ROADMAP.md][oldroadmap], [harness][harness], [test_rubric_cases.py][testrubric].

**Fix:** replace static counts with a generated summary or omit them; revise the roadmap against the pinned release state; add a real CI badge, license, minimal contribution guide, versioned results, and a release only when its claims are reproducible. Use a locked or constrained dependency set for published experiments; `verifiers>=0.3.0` and `cadquery>=2.8` alone do not freeze a result. **Where:** [pyproject.toml][pyproject].

## Recent research and what to use from it

The papers below are directly relevant to **CadQuery program generation, executable requirements, reward design, and engineering validity**. Dates are first arXiv submission dates unless noted. A paper's reported result is its authors' result, not a result established for `cad-spec`.

| Research | Finding relevant here | Concrete use in cad-spec |
|---|---|
| [CADEngBench: *It Looks Like CAD, but Does It Work?*](https://arxiv.org/abs/2608.09296) (Aug 2026) | Checks parametric perturbations, edits, engineering constraints, and FEA; visually plausible CAD may fail engineering behavior. | Add paired parameter-edit tests after the plate scorer is trustworthy; treat physics checks as a later, separate track. |
| [*Text-to-CAD Evaluation with CADTests*](https://arxiv.org/abs/2605.07807) (May 2026) and its [released code](https://github.com/dimitrismallis/CADTestBench) | Executable B-rep tests check geometric and topological requirements and can guide generation. | Position this repo as an RL environment with audited reward behavior; compare requirement pass/fail agreement and use mutation analysis. The basic “executable CAD tests” idea is no longer a distinct novelty claim. |
| [*Text2CAD-Bench*](https://arxiv.org/abs/2605.18430) (May 2026) | 600 curated examples span complexity levels and both geometric and procedural prompt styles. | Publish explicit difficulty tiers and prompt-style splits instead of one overall plate score. |
| [MUSE: *Benchmarking Manufacturable, Functional, and Assemblable Text-to-CAD Generation*](https://arxiv.org/abs/2605.28579) (May 2026; revised Jun) | Separates code validity, geometry, and design-intent criteria including manufacturability and assembly. | Use an explicit staged score report; label volume as a geometry proxy and introduce functional criteria only with stated engineering assumptions. |
| [BenchCAD: *A Comprehensive, Industry-Standard Benchmark for Programmatic CAD*](https://arxiv.org/abs/2605.10865) (May 2026) | Large multi-family CadQuery evaluation finds weak transfer to unseen part families. | Add held-out *family* evaluation before claiming broad generalization. |
| [*Improving Small Language Models for Code Generation with Reinforcement Learning from Verification Feedback*](https://arxiv.org/abs/2605.30478) (May 2026) | Reward design changes model behavior; diagnostics beyond pass@1 reveal failures. | Track code validity, token length, timeout, gate hits, per-requirement outcomes, and regressions alongside mean reward. |
| [*Beyond Binary: Turning Partial Success into Dense Verifiable Rewards for Reinforcement Learning in Code Generation*](https://arxiv.org/abs/2601.03525) (Jan 2026; revised May) | Partial-success reward can help but may favor easy checks unless calibrated. | Compare the present equal `k/7` reward with a gated, difficulty-aware alternative; publish per-check learning curves and guard against reward shortcuts. |
| [CAD-RL / ExeCAD: *From Intent to Execution*](https://arxiv.org/abs/2508.10118) (Aug 2025) and [CAD-Coder](https://arxiv.org/abs/2505.19713) (May 2025; NeurIPS 2025) | Both train models to produce executable CAD code using CAD-specific feedback; CAD-Coder also uses geometric similarity. | Include these as neighboring methods. Show where requirement-based checks add information beyond executability and shape similarity; do not claim a model improvement before a controlled run. |

**Research opportunity:** an evaluator that links each textual tolerance and datum to a specific measured B-rep feature, reports uncertainty at ambiguous geometry, survives adversarial mutations, and supplies calibrated partial reward. That combination would be more defensible than simply adding more families or another geometric-similarity term.

## Upgrade roadmap with acceptance gates

Effort ranges assume one experienced developer with occasional mechanical-design review. They are planning estimates, not commitments.

| Phase | Work | Deliverable and measurable exit gate | Effort |
|---|---|---|---|
| **0. Make claims reproducible** | Fix eager imports and quick starts; reconcile docs; freeze dependency versions; preserve a clean install recipe; save seed, model, prompt, code revision, and scorer revision for every run. | A fresh environment runs harness, pytest, lint, and type check from documented commands; a results JSON/CSV and short methods note reproduce one baseline. | 2–4 days |
| **1. Fix geometric truth** | Add datum/envelope coordinates and direct edge-margin checks; merge coaxial face depth intervals; add shifted-stock and split-bore cases; classify ambiguous/partial bores; test tolerance boundaries and balanced pocket/boss mutations. | Every known wrong part fails the intended named requirement; valid alternate modeling operations retain full credit; publish a reviewed mutation set and false-full-credit/false-rejection counts. | 1–2 weeks |
| **2. Contain generated code** | Execute each rollout in a disposable restricted environment; bound wall time, CPU, RAM, process count, output size, and disk; remove secrets/network where not needed. | State-leak and side-effect tests pass; the threat model says exactly what the runner isolates; scoring latency is measured. | 1–2 weeks |
| **3. Establish learning value** | Freeze train/eval splits and rubric; run at least two suitable local or hosted model baselines; train one adapter if baseline has useful spread; compare before/after with identical decoding settings and repeated seeds. | Report all-requirements pass rate, mean/median reward, per-check pass rate, parser failures, timeouts, gate hits, pass@1, confidence intervals, and representative failures. A claimed gain persists on the frozen eval split. | 1–3 weeks plus compute |
| **4. Prove transfer** | Keep plate template as Level 0; add unscaffolded prose, paraphrases, edited-spec pairs, then two carefully chosen new part families with independent feature detectors. Compare with a general CAD test benchmark where feasible. | Publish separate tier and held-out-family results; each new requirement has positive, negative, and reward-hack fixtures; at least one external benchmark comparison is reproducible. | 3–6 weeks |
| **5. Publish a research-grade release** | Create a data card, evaluation protocol, scorer changelog, known-failure taxonomy, license, and tagged release; consider expert review of a sampled test set. | Another person can run the benchmark and understand which claims apply to geometry, material volume, manufacturability, and generalization. | 1 week |

### Suggested evaluation protocol

1. **Freeze** prompt sets and scorer version before any training. Keep development, held-out parameter, paraphrase, and held-out-family splits distinct. Deduplicate by numeric tuple, wording template, and generated solution structure.
2. **Calibrate scorer against labeled geometry.** For each feature, create one-change mutants on both sides of every tolerance, plus benign variants. Two reviewers resolve any disputed expected result. Report false full credit and false rejection separately.
3. **Compare against simple baselines.** Include the exact template filled by a deterministic parser, a general code model, and the selected trainable model. The deterministic baseline exposes whether the prompt is mostly a number-copy task.
4. **Evaluate the training claim.** Fix sampling settings, evaluate several seeds, report uncertainty, and retain failed code and measurement summaries for diagnosis. Include an ablation of equal `k/7` reward versus any new reward design.
5. **Guard the release claim.** An 8/10 claim needs a reliable scorer, clean reproduction, and an actual improvement or diagnostic result. A 9/10 claim additionally needs convincing transfer beyond this single template and a meaningful comparison to contemporary CAD evaluation work.

## Verification note

The repository audit and split statistics are from the pinned source snapshot. The public four-job [CI run reports success](https://github.com/azzbilal/cad-spec/actions/runs/35865829883). In a clean local environment with CadQuery 2.8.0 and Verifiers 0.3.1, I ran **pytest: 44 passed**, **adversarial harness: 21/21 passed**, **Ruff: passed**, and **mypy: passed**. The two additional constructions described above were run through the unmodified scorer and produced rewards **1.000** and **0.000** respectively. No model training was run for this audit; the 8/10 and 9/10 targets are **conditional milestones**, not scores already achieved.
